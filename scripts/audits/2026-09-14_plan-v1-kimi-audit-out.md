## B 级（阻断实施）

**B-1 → P0-1 (b) + 假设 4：tmpdir 前缀判据有可证伪的失效路径**
问题：亲验输出中账本 project = `C:\Users\ADMINI~1\AppData\Local\Temp\r5-692zCI`，是 **8.3 短路径名**形式；而 `os.tmpdir()` 在运行期返回的是展开长名（`C:\Users\Administrator\...`）。前缀匹配将直接落空——修法 (b) 上线后 RED 依旧，P0-1 主目标不达成，且失败形态是"改了但没用"的静默。
依据：材料内联证据（P0-1 现象块的实测路径）。
建议修正案：比较前应当对两侧做路径规范化（realpath / 长短名统一 / 大小写归一），并将"规范化后匹配"本身纳入 R 回归用例（用短名形态 project 造一条测试账本行断言被跳过）。

**B-2 → P0-2 (a) vs P2-7：finish 落账构成 A3 双源，而替代路径缺关联键，两条路并存未裁决**
问题：流水 119/119 行已含 finish（单源已存在）。P0-2 (a) 把 finish/truncated 再写进账本 = 同一事实两个存储处，违反 A3；P2-7 备选"让 ④ 从流水取 finish"虽避开双源，但材料自己证明账本行**无 runId**（P0-1 根因段），账本↔流水无行级关联键，只能靠 ts+role+source 模糊匹配——脆弱且不可机检。方案对"④ 的数据源到底是账本还是流水"未作裁决，而两者后果相反：从流水取则历史 8 行 finish 齐全 → 收口立刻 RED，直接击穿 (c)"历史不追认"的承诺（重点面 4 的担忧在此路径下成立）。
建议修正案：应当先补行级关联键（账本与流水同写 runId/callId），再裁定 finish 唯一存放处（建议：流水为唯一真相源，账本只存派生的 `truncated` 布尔——派生判定不算双源，但须在方案中明文此推理）；并明文"④ 仅判含 truncated 字段的行，无字段行豁免"。

## W 级（应修）

**W-1 → P0-1 副作用缓解 + 全文 WARN/INFO 策略：与方案自引的 ORR-4 直接矛盾**
方案以 ORR-4"无量化防线则缓慢失守无报警"为 P3-2 的立项理由，却给 P0-1 误免、P2-1/2-3/2-5/2-6、P3-2 开了一串 **INFO/WARN 不阻断**药方，且无任何"谁看、何时看、连续几次升格"的消化机制。INFO 留痕 ≠ 报警。修正案：每新增一条 WARN/INFO 应当同时登记其升格条件与巡查时点（如收口摘要中强制计数回显 + 连续 N 次出现升 RED），否则宁缺。

**W-2 → P0-1 (c) 标"可选"不当**
假设 1 自述 3 行 mock 来自 cwd=技能根的演练，即**生成端至今不保证写临时账本**。只修判据端 (b) 不堵生成端，下一场手工演练可再造一批非 tmpdir 的脏行。修正案：(c) 应当升为必选，源头治理优先于判据豁免。

**W-3 → P0-2 (a)/(b) + 假设 7：截断判据用黑名单枚举，漏检面开放**
`finish∈{max_tokens,length}` 只覆盖已知的两家词表；GLM（z.ai）及其他兼容端点的截断终态词表**材料未给，不确定**。任何未知截断词将被当完整成功收下——正是本 P0 要消灭的假成功。修正案：应当反转为白名单——仅 `stop`/`end_turn`（及逐供应商确认过的完整终态）视为完整，其余一切值至少 WARN、审计岗 RED；词表存 org-config 而非硬编码进脚本。

**W-4 → P0-2 (b)：审计岗清单硬编码进 health-scan，构成岗位事实第二源**
`gate1-reviewer / auditor-readonly / drafter` 写死在检查里，与角色注册表重复声明（A3）。修正案："哪些岗位适用 ④"应当从角色注册表的机读标记派生。

**W-5 → P0-2 ④ 与 tmpdir 豁免（P0-1 b）的交互未定义**
若 ④ 也跳过 tmpdir project，则演练中的截断漏检可接受、但真实临时目录项目的截断同样免检（漏检面扩大且未披露）；若不跳过，mock 截断行会制造新 RED。修正案：应当明文各检查是否继承 project 豁免及理由。

**W-6 → P0-3 (a) 两处**
① "审查通过后升 RED"无判据、无时点、无责任人——愿望式升档（ORR-4 同构）。应当给量化升档条件（如白名单稳定 N 个收口、误报=0）。
② "实配模型名"扫描名单若硬编码进脚本，则名单本身成为 org-config 之外的供应商事实第二源（A3），且会随换配即腐。修正案：实配名/主机名清单应当从 org-config 动态派生后用于扫描；白名单存放位置与豁免语法须机读化并说明（注意白名单若放 .md 会自指命中，方案未交代）。

**W-7 → P2-1：findings/rejected 的机读来源未定义**
账本新增的 findings:{B,W,N} 由谁写入？若从审计报告正文解析，需先规定审计产出的机读格式；若由派发方凭 AI 自报数字入账，违反 D1（不信任自报）。修正案：应当先定义门一/门二报告的结构化尾栏（机读区），解析失败即拒收该笔 ok。

**W-8 → P2-2 + 假设 3：根因未明即立 RED，且消除路径可能被冻结件堵死**
假设 3 自认"疑为显式 --source 或链起点偏移"——两种解释下 RED 的正当性完全不同（前者违规、后者可能是合法流程）。且 auditor-readonly 固定 source=deepseek 写在被冻结/被 WIP 锁定的 06 体系中：若 drafter 默认链亦为 deepseek，则 RED 一旦触发**无合规出路**（改 06 违硬约束 1/3）。不确定：角色注册表是否在"v1.0 冻结核心原文"范围内，材料未界定。修正案：应当先完成归因再立判据；RED 上线前须明文"消 RED 的合法操作路径存在"。

**W-9 → P2-4：新旧 project 键并存期判据行为未定义**

## 总评

方案的三个 P0 **根因归属均成立**（P0-1 的 mock 不甄别、P0-2 的账本丢 finish 有流水 119/119 对照铁证、P0-3 的声明与正文矛盾），证据链质量高，假设清单自曝态度良好。但存在一个贯穿性内伤：**方案以"无报警则失守"（ORR-4）为诊断框架，开出的却是一大把不阻断、无升格机制的 INFO/WARN**——按它自己的第一性原理，这批新检查将在数月后成为下一批 ORR 教训素材。此外两处技术缺陷达阻断级：tmpdir 判据撞 8.3 短名（B-1）、finish 双源与关联键缺失未裁决（B-2）。
